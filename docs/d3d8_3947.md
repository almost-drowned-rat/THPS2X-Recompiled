# D3D8 3947 in THPS 2X – inventory for the HLE (M3.5 step 4a)

Static scan: direct calls from the game's `.text` into the D3D section (0x00011000–0x00028050): **65 functions,
876 call sites**; D3DX is barely used (2 functions, 6 sites). The game never touches the device pointer
`g_pDevice` (0x00028030) itself – all 166 references are inside the library – so there are **no inline
pushbuffer writes in game code**; everything goes through calls.

Runtime count: `tools\build.ps1 -Census` (`src/d3d_census.c`, strong overrides of the lifter's weak `sub_X`, no
re-lift) with `RECOMP_D3D_CENSUS=5` on the menu tour; 110 s of menus, 6606 frames at 60 Hz. **38 of the 65 are
called in the menus.**

## What the library looks like (matters for the HLE design)

- **Register arguments.** Hot internal entry points take arguments in `ecx`/`edx` (plus stack), like an LTCG
  build: `0x000146A0` SetTextureStageState(ecx = stage, edx = state, [esp+4] = value), `0x000145E0`,
  `0x00014610`. The HLE bindings read `g_ecx`/`g_edx`, not only the stack (XboxXBE-Recomp's `[abi]` table solves
  the same thing).
- **Deferred state.** Render and texture-stage state go into D3D's own arrays (render state 0x00025028, texture
  stage state 0x00024E28) with dirty bits (0x000254A8, masks 0x00023720 / 0x00024D68); the library encodes them
  into the pushbuffer lazily before a draw (`0x0001A370` reserve space and its callers).
- **Raw method writes from the game.** `0x000145E0` (153 calls/frame) appends two dwords – an NV2A method header
  (`ecx`) and its value (`edx`) – to the pushbuffer (`pPush` 0x000254A0, limit 0x000254A4, `0x0001A0D0` when
  full): `SetRenderState_Simple`-style. The game passes NV2A method numbers here, so even an API-level layer sees
  NV2A semantics for these; the HLE applies them straight to the renderer's state (the executor's method handler),
  without the memory round trip.

## HLE plan (step 4b, after the maintainer's go)

1. **Bind the draw path, keep the state model.** Override the draw calls (DrawVertices, DrawIndexedVertices,
   their UP variants) and the raw method writer: they read D3D's own state arrays and the bound
   textures/streams/shaders and record Vulkan work through `nv2a_vk` directly – the library's lazy pushbuffer
   encode (0x0001A370 path) and our executor's decode are skipped. Setters that only store into D3D's arrays
   (SetTextureStageState, SetRenderStateNotInline, SetTransform, SetStreamSource, SetIndices, SetTexture …) stay
   game/library code at first: they are cheap and keep the layout knowledge in one place.
2. **Present/Swap** bound next; it waits on the **real 60 Hz guest vblank** (maintainer note: one runtime clock
   both paths use, replacing the renderer-side sleep).
3. **Reference:** the pushbuffer path stays; every menu-tour shot is compared HLE vs pushbuffer automatically.
4. **No new Vulkan 1.3 requirement** (A11); render thread and the on-disk pipeline cache where cheap.

## NV2A methods without an executor case (M3.5 reduced 4b)

Menu tour with `RECOMP_PB_EXEC_VERBOSE=1 RECOMP_PB_UNHANDLED_ALL=1 THPS_LOG_RAW=1`: **263 distinct methods,
12.6 M calls** have no `case` in the executor. That number overstates the gap: every 3D-class method is stored in
the executor's register file first (`s_reg`, passed to the back end as `regs`), and the back end reads most state
from there – combiner stages and factors (`psh_key`, 0x0260/0x0AA0/0x0AC0/0x1E40/0x0A60/0x0A80 …), fog
(0x029C/0x02A0/0x02A4/0x09C0…), all texture-stage words (0x1B00 + 0x40·n, words 0–8), model view / inverse
(0x0480/0x0580, lighting and fog), lighting enable, stencil, clear rect. The executor now also records the OR of
every value a method carried (`or=` in the report).

- **148 methods are never set to anything but 0** in the menus: no effect (texgen modes, texture matrix enables,
  skinning, poly-offset enable, most light registers, …).
- **48 are set but read by nobody**; triaged:

## Level measurement and the full-HLE question (M4)

Free Skate, The Hangar, skater standing (`tests/input/level_freeskate.txt`, 108–128 s), 60 Hz guest vblank,
V-Sync on, RTX 3050 Ti. Sampling profiler `RECOMP_SAMPLE=108:128:500` (THPS `host_win32.c`, shares of the
busy samples).

Note on the frame-time counter: it belongs to the thread that runs the flip, and in THPS 2X that is the
executor (ack) thread. So "translate" is the executor's work and "game" is mostly its idle time; the game
thread's own load comes from the profiler and the per-thread CPU.

| Thread | Busy | Where |
|---|---|---|
| executor (ack) | 11 % of 16.67 ms ≈ **1.85 ms/frame** (frame-time "translate" 1.6–2.3 ms) | decode / method dispatch 45 % (`nv2a_pb_exec_method` 24, `nv2a_pb_scan` 6, `capture_render_state` 5, `nv2a_pb_exec_run` 4, `vp_method` 3, `note_unhandled` 2, immediate vertices 1); draw assembly 30 % (`memcpy` 9, `cull_batch` 7, `fetch_attr` 4, `tex_get` 4, `draw_primitive` 3, `upload_vertices` 2, program/pipeline lookup 2); Vulkan record 16 % (`vk_draw_raw` 8, NVIDIA driver 9) |
| game | 17 % ≈ 2.9 ms/frame | fence wait `sub_00019FE0` 18 % (waits for the executor; now sleeps), game code (`sub_00167C20` 13 %, D3D `sub_00014630` 6 %, …), `recomp_lookup` 3 % |

Decode + record stay **well above 1 ms** (≈ 1.85 ms ≈ 85 % of the CPU work besides waiting), so the effort for
a full D3D8 HLE for THPS 2X:

| Option | What | Saves (level) | Size / effort | Risk |
|---|---|---|---|---|
| A. Executor fast path (toolkit, all games) | table dispatch for the hot methods instead of the switch + register-file double write; vertex/index data bound from GPU-visible ring buffers instead of `fetch_attr` + `memcpy` per draw; `cull_batch` only where it pays | ≈ 0.6–0.9 ms (decode ~0.4, assembly ~0.4) | ~1–2 k lines changed, 4–6 sessions | low: pushbuffer semantics unchanged, Burnout 3 / Def Jam benefit |
| B. Register-level HLE (THPS) | override the D3D draw calls and the raw method writer; feed `nv2a_vk` the NV2A register state D3D's deferred arrays describe, skipping pushbuffer encode + decode | ≈ 0.8–1.0 ms (encode ~0.2 + decode ~0.8) | ~3–4 k lines (state model of 65 functions, `docs/d3d8_3947.md` inventory), 8–12 sessions | medium: the raw method writer (153 calls/frame) still speaks NV2A; two paths to keep in sync |
| C. Full API-level HLE (XboxXBE-Recomp style) | D3D8 → Vulkan directly: fixed-function T&L and texture stages → shaders, combiners, surfaces/readback, sync | ≈ 1.0–1.3 ms plus GPU-side vertex buffers | ~6–9 k lines (XboxXBE-Recomp `xdk/d3d8.cpp` + `gpu/` ≈ 6 k for D3D12), 20–30 sessions | high: reimplements what the pushbuffer path already does right; screenshot regressions likely |

Recommendation: A first (generic, cheap, measurable with the profiler), then B or C at the decision point
after the SCDA benchmark with the remaining numbers. At 60 Hz all of this is CPU/battery, not frame rate:
the frame is 16.67 ms and the executor needs < 2 ms.

### Option A, first stage – done (2026-10-16)

Toolkit `e9e6ee2` (`nv2a_pb_exec_run` bulk runs; `RECOMP_PB_FAST=0` = old path). Method histogram
(`RECOMP_PB_METHOD_STATS=1`) in the level before: 70 % of the data words went through the per-word dispatch, led by
SET_TRANSFORM_PROGRAM 0x0B00 (31 %: THPS 2X uploads a vertex program for most draws), vertex array formats 0x1760,
matrices 0x0480/0x0580/0x0680 and combiner registers. Now bulk: program uploads, composite matrix, vertex array
formats/offsets, and runs of *learned register-only* methods (fell through the whole default path once). After:
22 % per word (mostly one-word headers with real handlers: BEGIN_END 0x17FC, 0x1EA4, 0x0A20, clip range 0x0394).

| Level, standing, 60 Hz (`cpu_level.ps1`, sampler) | before | after |
|---|---|---|
| executor busy (share of wall time) | 11.7 % ≈ 1.95 ms/frame | 9.6 % ≈ 1.60 ms/frame |
| frame-time "translate" avg / p99 | 2.43 / 3.84 ms | 2.09 / 3.05 ms |
| decode share (exec_method + exec_run + scan + render state) | ≈ 0.88 ms | ≈ 0.41 ms |
| draw assembly (memcpy, cull_batch, tex_get, fetch_attr, upload, draw_primitive) | ≈ 0.55 ms | ≈ 0.61 ms |
| Vulkan record (vk_draw_raw + driver) | ≈ 0.30 ms | ≈ 0.36 ms |

CPU culling stays: it tests 289 of 390 draws a frame (0.42 µs each) and drops 44; without it the executor rose to
10.4 %. What is left is mostly copying vertex data into the Vulkan ring (`memcpy`, `fetch_attr`): only importing
guest memory as a Vulkan buffer (`VK_EXT_external_memory_host`, not on Android → optional path) would remove it;
`tex_get` (5.9 %) wants the dirty-page texture cache planned for after M4.

### Option A, stage 2 – shared page tracking (2026-10-16)

Toolkit `src/kernel/page_track.c` (A8): the contiguous window (both CPU aliases, 0x80000000 + P and the tiled
0xF0000000 + P) is tracked per 4 KB page. A consumer's check arms the pages read-only before it reads them; the
first guest write faults (THPS `host_win32.c` VEH → `xbox_PageTrackFault`), bumps the page's generation and goes on.
`NtReadFile` releases its target first (the OS would fail on a read-only page instead of faulting). Pages written
in 3 consecutive frames become "streaming" (not armed, always "changed"; retried every 600 frames).
`RECOMP_PAGE_TRACK=0` off, `RECOMP_PAGE_TRACK_STATS=1` counters.

- **Textures (`tex_get`):** no hash when the texture's pages are unwritten. Level: ~100 textures/frame checked,
  all unchanged, 0 faults; `tex_get` left the profile (was 5.9 % of the executor).
- **Vertex mirror (`nv2a_vk`, `RECOMP_VK_VMIRROR=1`, off by default):** device-local copy of the window in 4 MB
  chunks, pages copied in (staged through the ring, before the render pass) only when written; draws bind the
  mirror; ring path for streaming pages, chunk-crossing runs and pages rewritten after a draw of the frame read
  them. Works (98 % of the level's vertex runs from the mirror, a few page copies per 300 frames) but does not pay
  in THPS 2X: its vertex runs are small and the bookkeeping costs what the copies cost.

| Level, standing, 60 Hz | executor busy | translate avg / p99 | GPU avg |
|---|---|---|---|
| page tracking off (`RECOMP_PAGE_TRACK=0`) | 9.8 % | 2.11 / 2.94 ms | 2.31 ms |
| tracking, textures only (default) | **9.2 %** | **1.96 / 2.86 ms** | 2.29 ms |
| tracking + vertex mirror | 9.7 % | 2.06 / 2.96 ms | 2.33 ms |

The `memcpy` left in the profile (~10 % of the executor) is mostly the vertex-program constant block: 192 × 16 bytes
copied into the ring for every draw (~1.2 MB a frame at ~390 draws). Next lever: copy only the constants the program
reads (or only when they changed), keeping the instancing layout (`pend_append`) intact.
